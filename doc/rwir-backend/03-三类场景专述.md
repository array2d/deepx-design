# 03 — 三类场景专述

> 三类委托场景共享 01-注册发现 和 02-委托协议，本章专述各自特殊考量。

## 一、计算委托（tensor → op-gpu）

### 场景

kvlang 函数中的 tensor 操作委托给 GPU 后端执行：

```kv
rwfunc inference(x:tensor, W:tensor, b:tensor) -> (out:tensor) {
    tensor.matmul(x, W) -> tmp
    tensor.add(tmp, b) -> out
}
```

### 后端实现

op-gpu 是参考实现（详见 `doc/plans/op-gpu-scheduler/DESIGN.md`）：

```
/sys/rwir-backend/op-gpu/
├── status = "ready"
├── category/compute
├── op/tensor.matmul
├── op/tensor.add
├── op/tensor.relu
├── op/tensor.fused_linear_relu   # 融合算子
└── cmd                            # 命令队列
```

### 融合编译

op-gpu 的关键差异化能力：**融合编译**。多条连续 tensor 指令在 compile pass 合并为一条融合 rwir，减少 dispatch 往返次数：

```
# compile pass 前
tensor.matmul(x, W) -> tmp1
tensor.add(tmp1, b) -> tmp2
tensor.relu(tmp2) -> out

# compile pass 后（FUSE_DB 匹配 linear_relu）
tensor.fused_linear_relu(x, W, b) -> out
```

融合检测在 `compile.Fuse()` 中完成（编译期），委托协议本身不感知融合——它只看到单条 rwir。

### 设备亲和性

tensor 在创建时分配到特定 GPU，后续所有操作必须路由到同一 GPU。亲和性检查在 `Select()` 中完成：

```go
func SelectWithAffinity(kv kvspace.KVSpace, opcode string, tensors []ParamRef) (string, error) {
    // 1. 从第一个 tensor 的 address.device 读取 gpu_id
    // 2. 筛选 status=ready 且 device==gpu_id 的 backend
    // 3. 若无亲和 backend → error（需显式 tensor.move）
    // 4. 在亲和 backend 中选 load 最低者
}
```

亲和性信息从 `RwirTask.inputs[0].address.device` 获取。

### 编译缓存

编译产物（`.so`）缓存在 `/func/compiled/<pattern>/<shape_hash>/`，所有 op-gpu 实例共享。委托时 task 携带 `kernel` 字段指向缓存路径，op-gpu 按需 dlopen。

## 二、API 封装（LLM → rwir）

### 场景

将 LLM API 调用封装为 rwir 指令，使 kvlang 代码可以像调用内建算子一样调用 LLM：

```kv
rwfunc analyze(code:string) -> (result:string) {
    llm.chat("/session/42") -> resp      # 发送消息列表，获取回复
    llm.embed("hello world") -> vec       # 获取 embedding
}
```

### 异步模型

**关键设计**：LLM 调用必须异步。HTTP 请求可能耗时 30s+，同步阻塞会耗尽 kvcpu worker pool。

```
kvcpu worker                    llm_worker (独立 goroutine pool)
─────────────                   ─────────────────────────────────
│                               │
│ llm.chat → Delegate()         │
│   → Notify(cmd_queue)         │
│   → Set(pc, "wait")           │
│   → Watch(done_key) → 阻塞    │
│                               ├─ Watch(cmd_queue) 触发
│                               ├─ 读 session messages
│                               ├─ HTTP POST → LLM API
│                               ├─ 写 response 到 session
│                               └─ Notify(done_key)
│                               │
│ Watch 返回 → 推进 PC          │
▼                               ▼
```

llm_worker 是 kvlang 进程内的独立 goroutine pool（或独立进程），与 kvcpu worker pool 完全解耦。两者数量独立配置：

```
kvcpu workers: 8   ← 执行 kvlang 指令的 goroutine
llm_workers:  16   ← 发送 HTTP 请求的 goroutine（可大于 kvcpu，因为多数时间在等 I/O）
```

### session 约定

LLM 调用的上下文通过 session 路径传递。session 是 `/session/<id>/` 下的消息树：

```
/session/<id>/
├── model     = "claude-sonnet-5"
├── system    = "You are a helpful assistant."
├── msg/
│   ├── count = "3"
│   ├── 0/
│   │   ├── role = "user"
│   │   └── text = "say hello"
│   ├── 1/
│   │   ├── role = "assistant"
│   │   └── text = "Hello! How can I help?"
│   └── 2/
│       ├── role = "user"
│       └── text = "what is kvlang?"
└── result/
    └── <call_id>/
        ├── text = "kvlang is ..."
        └── usage = "{\"input\":150,\"output\":200}"
```

`llm.chat` 的 input 是 session_id（字符串），不是 session 内容本身。llm_worker 根据 session_id 自行读取消息树、调 API、写入结果。

### RwirTask 示例

```json
{
  "request_id": "rwir:llm_worker:7:15",
  "vtid": "7",
  "pc": "/vthread/7/[3,0]",
  "opcode": "llm.chat",
  "inputs": [
    {"key": "/session/42", "dtype": "string"}
  ],
  "outputs": [
    {"key": "/vthread/7/[0,0]/resp", "dtype": "string"}
  ],
  "params": {
    "max_tokens": 4096,
    "temperature": 0.7
  }
}
```

### 限流与重试

llm_worker 自行管理 API key、rate limit、重试。RwirTask 的 `params` 可携带重试策略覆盖：

```json
"params": {
  "max_tokens": 4096,
  "retry": {"max": 3, "backoff": "exponential", "initial_ms": 1000}
}
```

默认重试策略由 llm_worker 配置决定，`params.retry` 为可选覆盖。

## 三、Agent 封装（agent → rwir）

### 场景

将一个完整 agent 的执行封装为单条 rwir 指令。调用方不感知 agent 内部的 tool use 循环——它看到的是一个原子操作：

```kv
rwfunc code_review() -> (bugs:list) {
    agent.search("kvlang runtime memory leaks", "codebase") -> findings
    agent.analyze(findings) -> report
}
```

### 实现：sub-agent = vthread

agent 后端在收到委托后，**spawn 一个子 vthread** 来执行 agent 循环。这是 kvlang 最自然的方式——vthread 的创建成本是一次 KV 写入，不需要新进程。

```
kvcpu (主 vthread)              agent_pool (后端)             子 vthread
──────────────────              ────────────────             ──────────
│                               │                            │
│ agent.search(...)             │                            │
│ → Delegate()                  │                            │
│   → Notify(cmd_queue)         │                            │
│   → Watch(done_key)           │                            │
│                               ├─ Watch 触发                 │
│                               ├─ 解析 task                  │
│                               ├─ Bootstrap 子 vthread:      │
│                               │   vthread.CreateVThread()   │
│                               │   layout.Bootstrap()        │
│                               │   kv.Notify(vt_schedule)    │
│                               │                            │
│                               │                          ┌─ kvcpu pick 子 vthread
│                               │                          │  Execute(agent_loop)
│                               │                          │  ├─ llm.chat
│                               │                          │  ├─ tool.call
│                               │                          │  ├─ llm.chat
│                               │                          │  └─ ... (多轮循环)
│                               │                          │  vthread.SetDone
│                               │                          └─ Notify(done_key)
│                               │                            │
│                               ├─ Watch 子 vthread 终态     │
│                               ├─ 读结果                    │
│                               └─ Notify(done_key)          │
│                               │                            │
│ Watch 返回 → 推进 PC          │                            │
▼                               ▼                            ▼
```

### agent_pool 后端

agent_pool 不是一个执行 agent 循环的进程——它是 agent 的**调度器**。它的职责：

1. 接收 agent 委托请求
2. 准备子 vthread 的输入（写入 kvspace）
3. 创建子 vthread（`CreateVThread` + `Bootstrap`）
4. 等待子 vthread 完成
5. 读取结果，Notify 完成信号给主 vthread

agent_pool 不需要自己实现 agent 循环——agent 循环是普通的 kvlang 函数，由标准 kvcpu 执行。

### agent 函数签名约定

被委托的 agent 函数必须遵循标准签名：

```kv
rwfunc agent_search(query:string, domain:string) -> (findings:string) {
    # agent 循环：多轮 llm.chat + tool.call
    session.create("claude-sonnet-5", "/sys/prompts/search_agent") -> sid
    msg.append(sid, "user", query)
    
    max_rounds -> rounds
    while (rounds < 10) {
        llm.chat(sid) -> resp
        stop_reason(resp) -> sr
        if (sr == "end_turn") { break }
        dispatch(resp, sid) -> ()
        rounds + 1 -> rounds
    }
    
    msg.last_text(sid) -> findings
}
```

agent_pool 通过 `vthread.CreateVThread("agent_search", [query, domain], ["findings"])` 创建子 vthread——参数传递完全复用现有 rwfunc 调用机制。

### 超时与取消

agent 委托的超时（默认 300s）比计算/API 长得多。超时后：

```
1. kvcpu Watch(done_key) 超时
2. kvcpu 写 /vthread/<child_vtid>/.debugger = "abort"
3. 子 vthread 在下一个 debugger 检查点终止
4. kvcpu 调用 vthread.SetError 标记主 vthread 超时
```

### 与 livebyte 的关系

livebyte 是 agent 委托的第一个使用者。它的 `subagent.spawn` 和 `subagent.await` builtin 直接映射到本协议：

```kv
# livebyte 中的写法
subagent.spawn("code_review", prompt) -> vtid
subagent.await(vtid, 300) -> result

# 对应的委托协议
# RwirTask { opcode: "agent.spawn", params: {agent: "code_review", ...} }
# → agent_pool 创建子 vthread → 返回 vtid
# RwirTask { opcode: "agent.await", inputs: [{key: vtid_status}] }
# → agent_pool Watch 子 vthread 终态 → 返回 result
```

注意 livebyte 将一个 agent 委托拆成两条 rwir（spawn + await），而非单条阻塞 rwir。这允许主 agent 在等待子 agent 期间继续执行其他指令（如发起多个并行子 agent）。委托协议本身不强制同步或异步——由 rwir 的粒度和 kvcpu 的等待策略决定。
